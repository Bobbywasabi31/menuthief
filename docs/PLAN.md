## 1. The product in one paragraph

A map that shows **only food**. You browse restaurants, cafés, bakeries and food trucks around you, tap one, read its **actual menu**, tap a dish — and get a **home-cookable recipe for that dish**: ingredients, quantities, steps, time, and a grocery list. The moment it serves: *"I saw it on their menu — now I want to make it."*

Core loop: **Map → Place → Menu → Dish → Recipe → (save / share / grocery list)**

Differentiation, checked 2026-10-27:

- **Snappy Menu** (closest existing app) does menu → recipe, but it's camera-first: you're already seated, scanning a physical menu. Nobody found does the **map-first** version — discover a real place near you, open its real menu, cook from it.
- A chatbot can invent a recipe from a dish name, but it can't show you the actual menu of the place two blocks away. The moat is the **live local discovery + real menu** layer, not the recipe text.
- Framing rule (borrowed from Snappy Menu, it's the honest one): recipes are **home versions inspired by the dish**, never claimed to be the restaurant's own recipe. Say so in the UI on every recipe.

## 2. MVP scope

### In
- Food-only map (restaurants, cafés, fast food, bakeries, bars with food, food trucks) centered on the user, pan/zoom refetch
- Place card: name, cuisine, address, hours if available, rating if available
- Menu view for a place, obtained via the tiered pipeline in §5, with **source + date shown** ("from the restaurant's website, fetched today" / "from a menu photo")
- Tap a dish → generated recipe (structured, §6), servings scaler, grocery list
- Save recipes locally; share a recipe (or place+dish) as a **compressed-state URL** — the Daily Income Machine pattern, no backend, no accounts
- Fallback: if no menu exists for a place, user can **paste a menu link or snap/upload a menu photo** and get the same dish → recipe flow

### Out (v1+ candidates, not MVP)
- Accounts, sync, social anything
- Ordering/delivery integration
- Persisted server-side database of menus (also a ToS hazard — see §9)
- Native apps (web PWA first; it wraps later if it earns it)
- Nutrition/allergen certification — show a caution line, never a guarantee

## 3. Architecture

Deliberately boring, matches Alex's existing stack:

- **React** single-page PWA, mobile-first layout (map top, sheet-style place/menu/recipe panels — this is a phone use case)
- **Leaflet** for the map; OSM raster tiles for the prototype (attribution shown; swap to a hosted tile provider — Stadia/MapTiler free tier — if usage grows past OSM tile fair-use)
- **No backend in MVP.** Two external dependencies are called client-side: the places provider and the LLM (see §7 for the key problem and the plan for it)
- **Places provider is an interface, not a vendor.** `PlacesProvider.searchNearby(bounds, categories)`, `PlacesProvider.getPlace(id)` — two implementations:
  - **v0: Overpass API (OpenStreetMap)** — free, no key, global. Query `amenity ∈ {restaurant, cafe, fast_food, food_court, bar, pub, bakery…}` plus `shop=bakery` within the map bounds. Public-instance fair use is roughly <10,000 queries/day — a personal MVP is nowhere near that. Debounce map moves, query on bounds-change only, cache results per bounds in memory/localStorage.
  - **v1 (if it earns it): Google Places API (New)** — better coverage, ratings, photos (photo route feeds menu Tier 1 below). Costs in §8. Google shows menus in its own UI but the **API does not return menu items** — Places upgrades discovery and photos, it does *not* solve menus.
- State: localStorage for saved recipes + cached menus; shareable state compressed into the URL hash (lz-string), same as Daily Income Machine.

## 4. Data model

```jsonc
// Place
{ "id": "osm:node/123456", "name": "…", "lat": 32.71, "lon": -117.16,
  "categories": ["restaurant"], "cuisine": "mexican", "address": "…",
  "website": "https://…", "openingHours": "…", "rating": null }   // rating only via Places v1

// Menu — always carries provenance; a menu without a source is not shown as fact
{ "placeId": "osm:node/123456",
  "source": "website" | "place_photo" | "user_photo" | "user_link",
  "sourceUrl": "https://…", "fetchedAt": "2026-10-27T…",
  "confidence": "high" | "medium" | "low",
  "sections": [ { "name": "Mains", "price_note": null, "items": [
      { "name": "Baja Fish Tacos", "description": "beer-battered cod, chipotle crema…",
        "price": 16.50,
        "variants": [ { "label": "Steak", "price": 18.00 } ] } ] } ] }

**Schema decision (2026-10-28, from M0 evidence — decided before M1 so the UI is never built on the flat model):** variant pricing is the norm, not the exception (protein choices, 6 vs 12 pc, cup vs bowl, pours, add-ons, prix-fixe courses with no per-item price). So: an item's `price` is the base/default price (or null), `variants` is an optional list of `{label, price}` for priced alternatives and add-ons, and a section may carry a `price_note` (e.g. "3-course, $59") for bundle-priced sections whose items have null prices. M0's grading run modeled variants as separate items; that was a grading expedient, not the schema — extractions going forward use `variants`, and the M0 validator accepts both.

// Recipe — generated, labeled inspired-by
{ "dishName": "Baja Fish Tacos", "placeName": "…", "servings": 4,
  "timeMinutes": 35, "difficulty": "easy" | "medium" | "hard",
  "ingredients": [ { "item": "cod fillets", "qty": 600, "unit": "g", "note": "…" } ],
  "steps": ["…"], "swaps": ["…"], "mode": "closest" | "quicker" | "healthier" }
```

## 5. The menu problem (the whole game)

Places APIs give you the restaurant, never the menu. Three tiers, tried in order, first success wins; every tier produces the same `Menu` object with its provenance set:

- **Tier 1 — Menu photos (Places v1 only).** Google place photos very often *are* menu photos. A vision model reads the photo → structured menu. Confidence medium; label "from a menu photo."
- **Tier 2 — Restaurant's own website.** Follow the place's website/menu link, fetch the menu page or PDF, LLM-structure the text into sections/items/prices. This is the best source when it exists: current, complete, restaurant-published. Confidence high. (Fetch happens client-side where CORS allows; where it doesn't, this tier needs the §7 proxy — acceptable for MVP to skip-and-fall-through on CORS failure.)
- **Tier 3 — User-provided.** User uploads/snaps a menu photo (vision extraction, same as Tier 1) or pastes a menu URL. Always available, zero coverage problem, and it's the demo path: the app works for *any* restaurant the day it ships if the user feeds it one photo.
- **No menu at all →** place card shows "No menu found — add one" (Tier 3 prompt) plus, optionally, popular dish names mined from reviews (Places v1) as recipe starting points, clearly labeled as review-derived, not a menu.

Caching: extracted menus cached in localStorage keyed by place id + source URL; show the fetch date; a "refresh" re-runs the tier.

## 6. Recipe generation contract

One LLM call per dish, structured JSON out (schema above; reject-and-retry once on invalid JSON).

Prompt inputs: dish name, menu description (the single biggest quality lever — a description is half a recipe), cuisine tags, place name/type. Requirements baked into the prompt:

- Home kitchen only: no commercial equipment, ingredients buyable at a normal grocery store, quantities in grams *and* US units
- Servings default 2–4, scaler multiplies quantities client-side (store base quantities, scale in the UI — don't re-call the LLM to scale)
- Modes: **Closest taste** (default), **Quicker** (≤30 min, shortcuts allowed), **Healthier** (swaps) — a mode is a prompt variant, cheap to offer, and it's what the photo-to-recipe apps already train users to expect
- Grocery list = ingredients minus a built-in "pantry staples" list (salt, oil, flour…), grouped by store section
- Honesty line rendered under every recipe: *"A home version inspired by this dish — not the restaurant's recipe."*
- Allergen caution line, generic: *"Kitchens and recipes vary — check ingredients against your allergies."*

## 7. The LLM key problem (decide before building)

Client-side-only means an LLM API key can't ship in the app. Three options, in MVP order:

1. **Bring-your-own-key (MVP default):** user pastes their own OpenAI/Anthropic/Gemini key once; stored in localStorage only. Zero cost to run, zero backend, fine for a personal/friends beta. Vision-capable model required (menu tiers 1 & 3).
2. **Local model:** Ollama on the user's machine (Alex's 3080 Ti) — fully local-first, but only works on his desk setup, not phones. Optional config, not the default path.
3. **Thin proxy (v1, if it goes public):** one small serverless function holding the key, rate-limited per IP. This is the *only* backend the product ever needs. Also unblocks Tier 2 fetches that fail CORS.

## 9. Risks & hard rules

- **Don't scrape delivery platforms** (DoorDash/Uber Eats have the best structured menus and the clearest ToS prohibition). Not a data source. Same for scraping Google Maps itself.
- **Google data:** if Places is adopted, its terms restrict storing content (place IDs are the durable key; don't build a permanent database of Google-sourced content). The OSM route has no such issue — ODbL attribution is the only obligation.
- **Menu staleness:** menus change; provenance + fetch date on every menu is the mitigation, plus one-tap refresh. Never show a menu without its source.
- **Coverage reality:** many small places will hit Tier 3 or nothing. That's why Tier 3 is in the MVP, not a later patch — the app must never dead-end at a place with no findable menu.
- **Recipe quality variance:** dish name alone gives generic output; description-bearing dishes will be visibly better. Set expectations in the UI ("menus with descriptions give better recipes") and let users edit/save their tweaks on a saved recipe.
- **The chatbot test:** the recipe call alone is commodity. The product is map + real menu + one tap. If a build milestone doesn't strengthen that chain, it's scope creep.

## 10. Test set (build against these, not vibes)

Pick 10 real restaurants near Alex covering the hard cases, and grade every milestone against them:

1. Chain with a published web menu (Tier 2 should nail it)
2. Local place whose menu is a PDF on its site
3. Local place with menu photos on Google but a thin website (Tier 1 case)
4. Food truck / taqueria with no website (Tier 3 or nothing)
5. Bakery/café (different category + hours behavior)
6–10. A spread of cuisines (Mexican, Thai, Italian, BBQ, vegan) incl. one place with specials that change

**Acceptance targets:** menu obtained for ≥7/10 without user help; ≥10/10 with Tier 3; recipe generated for 100% of menu items tapped; a saved recipe re-opens from its share URL in a fresh browser with no state.
